# Методика: эффективность отработки задач воронки

Отчёт оценивает, как сотрудники канала УЗП отрабатывают задачи на
**привлечение, расширение, запуск и активацию** зарплатных проектов: что
получено по результату, как соблюдается дисциплина и есть ли признаки того,
что показатели набраны формальными закрытиями.

Все числа в документе получены **запуском кода** на синтетической базе
открытого контура (`python3 -m synth_tasks` → `python3 -m synth_tasks.verify`),
отчётный месяц **2026-08**, дата среза **2026-08-31**. Это проверочные цифры,
не промышленные: на проме значения будут другими, а формулы теми же.

---

## 1. Источник и грейн

| | |
|---|---|
| Основная витрина | `s_grnplm_ld_salesntwrk_pcap_sn_uzp.uzp_dwh_sale_funnel_task` |
| Потенциал клиента | `…uzp_data_emp_potential` (уровень `lvl_name = 'gosb'`) |
| Грейн витрины | одна строка = задача в конкретном **месячном снимке** `report_dt` |
| Ключ задачи | `task_code` |

**Задача живёт в нескольких снимках.** Пока она не закрыта, она повторяется из
месяца в месяц. Поэтому в каждом запросе стоит дедупликация:

```sql
row_number() OVER (PARTITION BY task_code ORDER BY report_dt DESC) = 1
```

Берётся последнее известное состояние задачи на дату среза. Без этого
долгоживущая задача считалась бы столько раз, сколько месяцев она висит, и
«дисциплина» тем выше, чем дольше сотрудник тянет. Проверка: в прогоне за
2026-08 после дедупликации **0 повторов** `task_code` (печатается в
`synth_tasks.verify`).

### Отбор задач

```sql
task_create_dt BETWEEN :dt_from AND :dt_to        -- месяц ПОСТАНОВКИ задачи
AND (task_type IN ('Привлечение ЗП', 'Расширение ЗП', 'Активация')
     OR COALESCE(task_subtype, '') ILIKE '%апуск%')
```

Отдельного типа «Запуск» в витрине нет — запуск проходит подтипом внутри
активации, поэтому к списку типов добавлен поиск по подтипу. Список типов —
параметр тетрадки (`task_types`), менять его можно не трогая код.

Отчётный месяц — **месяц постановки** задачи, а не закрытия: иначе задачи,
поставленные в августе и закрытые в сентябре, выпали бы из оценки августа, а
«хвост» июльских задач попал бы в августовскую конверсию.

### Дата среза

`as_of` — снимок витрины, на котором смотрим отработку. По умолчанию берётся
последний доступный, и об этом печатается предупреждение. Чем позже срез, тем
больше отработки видно: задача, поставленная 28 августа, к 31 августа честно
может быть ещё открыта.

## 2. Признаки на задаче

Сначала на каждой задаче считаются простые булевы признаки, и только потом они
сворачиваются в доли. Любое число дэшборда раскрывается до перечня задач.

| Признак | Формула | Смысл |
|---|---|---|
| `cycle_days` | `fact_close_task_dttm − task_create_dt`, в днях | время отработки |
| `same_day` | дата закрытия = дата постановки | закрыта в день постановки |
| `overdue_closed` | `fact_close > plan_close` | закрыта с просрочкой |
| `overdue_open` | не закрыта и `plan_close < as_of` | висит с истёкшим сроком |
| `stale` | не закрыта и возраст ≥ 30 дн. | зависшая |
| `no_footprint` | закрыта и `last_active_dttm IS NULL` | закрыта без цифрового следа |
| `stub_comment` | закрыта и длина комментария < 30 симв. | формальный комментарий |
| `clone_comment` | `md5` комментария повторяется у сотрудника ≥ 3 раз | клон |
| `quest_filled` | анкета не пуста | заполнен чек-лист |
| `low_value_success` | успех и (`fact_qty ≤ 1` или `fact_qty/plan_qty ≤ 0,10`) | успех без результата |
| `burst_close` | закрытие попало в «день зачистки» (см. ниже) | массовое закрытие |
| `conveyor_close` | закрытие входит в серию ≥ 5 задач с интервалом ≤ 5 мин | конвейер |

Длинные тексты (`task_comment`, `task_questionnaire`, `task_text`) **из БД не
выгружаются**: в SQL считаются длина и отпечаток `md5`. Отпечатка достаточно,
чтобы поймать один и тот же комментарий на десятках задач, а сам текст для
этого не нужен — и память ядра остаётся свободной.

### День зачистки (массовое закрытие)

День считается днём зачистки, если выполнено **любое** из двух условий:

```
(закрытий за день ≥ 10  И  ≥ 30 % месячных закрытий сотрудника)
или
(закрытий за день ≥ 5   И  ≥ 50 % месячных закрытий сотрудника)
```

Первое условие ловит крупный поток, второе — сотрудника с небольшой нагрузкой:
при 14 закрытиях за месяц порог «10 за день» недостижим, хотя 7 задач из 14 в
один день — это та же зачистка. Одного абсолютного порога мало: 10 задач из
200 за месяц — просто продуктивный день.

### Конвейер

Закрытия сотрудника упорядочиваются по времени; соседние, отстоящие не больше
чем на 5 минут, склеиваются в серию. Серия от 5 задач помечается: прочитать
задачу, связаться с клиентом и записать результат за это время нельзя.

## 3. Комплексная отработка клиента

По одному клиенту задач бывает несколько, и отдельная задача ничего не говорит
о клиенте. Свод строится по `inn` по **всем** его задачам отчётного месяца:

| Метрика | Правило |
|---|---|
| Статус | `Отработан полностью` (закрыты все задачи), `Отработан частично`, `Не начат` |
| `contradiction` | по клиенту есть и успех, и «невозможно отработать» |
| `sweep` | задач ≥ 2 и все закрыты **одним календарным днём** |
| `no_footprint_all` | есть закрытые задачи и ни одной активности |
| `fill_rate` | факт получателей ÷ план получателей, **по успешным задачам** |
| `potential_rate` | факт получателей ÷ потенциал численности организации |

`sweep` намеренно не требует, чтобы это был один сотрудник: если по клиенту
работают двое и оба закрыли свои задачи в один день, это та же зачистка.

Проверочный прогон за 2026-08: клиентов **9 097**, из них отработано полностью
**4 508**, частично **1 446**, не начато **3 143**. Клиентов с двумя и более
задачами — **2 729**, полностью отработано из них **904**.

## 4. Дни без цифровых следов

След — это закрытие задачи, зафиксированная активность (звонок, встреча) или
заведение сделки. Следы собираются по **всем типам задач**, а не только по
целевым: день, потраченный на отток или сервис, прогулом не является.

```
немые дни = рабочие дни месяца − дни, в которые есть хотя бы один след
доля немых дней = немые дни ÷ рабочие дни месяца
```

В августе 2026 — **21 рабочий день**. Средняя доля немых дней в проверочном
прогоне — **30,3 %**.

---

## 5. Показатель «факт к плану получателей»

Считается **только по успешным задачам**:

```
fill_rate = Σ fact_staff_deal_qty (успешные) ÷ Σ plan_staff_deal_qty (успешные)
```

Если брать все задачи, в знаменатель попадает план ещё не закрытых и отказных
задач, где факта нет и быть не должно, и показатель превращается в «сколько
задач закрыто». Проверочный прогон: план **251 156** чел., факт **125 517**
чел., `fill_rate` = **50,0 %**.

## 6. Интегральные индексы

Каждый компонент делится на управленческую планку из `config.NORM`, обрезается
в [0, 1] и умножается на вес. Планка — норма, а не статистика по выборке: иначе
при общем ухудшении оценки остались бы прежними.

**Индекс результата (0-100)**

| Компонент | Вес | Планка = 100 баллов |
|---|---|---|
| успех от закрытых | 0,40 | 35 % |
| факт к плану получателей | 0,30 | 70 % |
| клиенты, отработанные полностью | 0,30 | 80 % |

**Индекс дисциплины (0-100)**

| Компонент | Вес | Формула |
|---|---|---|
| отсутствие просрочки | 0,30 | `1 − доля просроченных` |
| присутствие в системе | 0,25 | `1 − доля немых дней` |
| содержательность записей | 0,25 | `0,6·(1 − доля формальных) + 0,4·заполненность анкет` |
| скорость | 0,20 | `(2·14 − медиана цикла) ÷ 14`, обрезано в [0, 1] |

Медиана 14 дней и быстрее — 100 баллов, 28 дней и дольше — 0.

**Индекс риска (0-100)** — приоритет ручной проверки, а не обвинение:

```
risk = 100 · Σ вес · min(1, доля ÷ порог)
```

| Признак | Вес | Порог |
|---|---|---|
| закрытия в днях зачистки | 0,25 | 30 % |
| конвейер | 0,20 | 15 % |
| успехи без результата | 0,20 | 50 % |
| закрытия без следа | 0,15 | 50 % |
| клоны комментариев | 0,10 | 40 % |
| закрытие в день постановки | 0,10 | 40 % |

При числе закрытых задач меньше 10 индекс уменьшается вдвое: на малой выборке
доли скачут от 0 до 100 % и говорят о размере выборки, а не о поведении.

## 8. Проверка, что триггеры ловят то, что должны

`python3 -m synth_tasks.verify` сверяет отчёт с правдой, заложенной в
синтетику: каждый сотрудник синтетической базы имеет архетип поведения, и
скрипт считает, какая доля носителей архетипа поймана соответствующим
триггером. Результат последнего прогона (среди сотрудников с 10+ закрытыми
задачами — область применимости триггеров):

| Архетип | Триггер | Поймано |
|---|---|---|
| массовое закрытие | `flag_burst` | 85,4 % |
| зачистка клиентов | `flag_sweep` | 61,1 % |
| успех на минимальном потенциале | `flag_low_value` | 96,6 % |
| закрытие в день постановки | `flag_same_day` | 100 % |
| молчун | `flag_silent_days` | 100 % |
| отказник | `flag_refuse` | 100 % |
| клонированные комментарии | `flag_clone` | 100 % |

**Ложная тревога на добросовестных сотрудниках — 4,9 %** (допустимо до 25 %).

Средний индекс риска по архетипам: добросовестные **8,9**, «зачистщики»
**88,4**, «массовые закрывальщики» **83,0**. Разделение устойчивое.

## 9. Проверка сходимости

В каждом прогоне (`analysis.check`) проверяется:

- сумма задач по ТБ = сумма по сотрудникам = сумма по клиентам = общее число;
- ноль повторов `task_code` после дедупликации снимков;
- нет задач, помеченных успехом без закрытия;
- расчётная просрочка сходится с текстовым статусом витрины в пределах 10 %.

Расхождения не прячутся: печатаются в прогресс и выводятся отдельным блоком в
шапке дэшборда. В последнем прогоне расхождений нет.

Про сверку просрочки: задачи со статусом «невозможно отработать» из неё
исключены — витрина ставит этот статус **вместо** отметки о просрочке, поэтому
по датам они просрочены, а по статусу нет. Это приоритет статусов в источнике,
а не ошибка расчёта.

## 10. Известные ограничения

1. **Цифровой след виден только внутри воронки.** Закрытие задачи, активность,
   заведение сделки. Работа в других системах в этой витрине не отражается,
   поэтому «немой день» означает «нет следа в воронке», а не «не работал».
2. **Производственного календаря нет.** Рабочими считаются будни; праздники
   попадают в знаменатель немых дней. Поправка одинакова для всех сотрудников.
3. **Время постановки задачи — дата без часов.** Цикл считается от начала дня
   постановки, закрытие в тот же день даёт цикл 0. Поэтому «закрыто за час»
   отдельно не измеряется — измеряется «закрыто в день постановки».
4. **Успех берётся из витрины** (`is_task_closed_success`) и не
   пересчитывается. Отчёт добавляет к нему меру результата (получатели), но не
   спорит с флагом источника.
5. **`unrealized_deal_potential`** в расчётах не используется: в витрине он
   заполнен у 44 % строк, и его знак трактуется источником неоднозначно.
   Вместо него берутся `plan_staff_deal_qty` и `fact_staff_deal_qty`.
6. **Потенциал численности** (`uzp_data_emp_potential`) — один снимок без
   истории. Если на дату среза его нет, отчёт считается без метрики «факт к
   потенциалу», о чём печатается предупреждение.
7. **Средняя доля немых дней по подразделению** — среднее по сотрудникам, а не
   взвешенное по задачам: единица наблюдения здесь сотрудник, а не задача.
   Остальные доли в сводах считаются от сумм.
8. **Отчёт ничего не доказывает.** Триггер — это повод открыть карточки задач
   и посмотреть, была ли работа. Индекс риска сортирует очередь проверки.

## 11. Как воспроизвести числа

```bash
docker start uzp_pg                 # локальный Postgres открытого контура
python3 -m synth_tasks              # синтетика по профилю витрины
python3 -m synth_tasks.verify       # проверка: ловятся ли архетипы + все числа
python3 -c "import uzp_tasks; uzp_tasks.run(report_month='2026-08')"
```

На закрытом контуре запускается `run_tasks.ipynb`: та же функция `run()` с
параметрами подключения к пром-БД. Синтетика там не нужна — схема и имена
таблиц совпадают, SQL переносится без правок.
